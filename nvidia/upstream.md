# NVIDIA input provenance

[upstream.json](upstream.json) records NVVM, NVRTC, nvJitLink, nvFatbin, Compute Sanitizer and cuDNN generation. Other
approved NVIDIA packages are not yet recorded; they remain in scope. This is
partial provenance, not release readiness, complete API coverage, a runtime
support matrix, or a claim that the build is hermetic.

Schema version 1 contains package entries with repository commits and Git tree
identifiers, vendor archive and header hashes, documentation inputs, the generator
command, and SHA-256 hashes of every generated output. Paths within entries are
relative to the named repository root; output paths are relative to the lib root.
The lib commit identifies the output comparison snapshot, not the commit that
first contains this manifest. Repository commits identify complete source inputs;
the documentation subtree includes every `*-docs.json` merged by the generator.

Recorded commits may currently exist only in local repositories; this manifest
does not establish that they are available from a public remote.

To reproduce an entry:

1. Obtain each named repository and create clean checkouts at its recorded commit.
2. Verify the Git tree identifiers and header SHA-256. The vendor archive hash and
   member path allow a separate check against the original archive.
3. Set `CODEGEN_REPO` and `HEADERS_REPO` to those checkout roots. Set `OUTPUT_DIR`
   to an empty scratch directory and `SCRATCH_DIR` to an existing temporary-work
   directory, outside any repository.
4. Run the recorded argv from `CODEGEN_REPO`, substituting those placeholders
   literally, with the recorded environment and toolchain. The argv is an array,
   not a shell command to evaluate.
5. Compare the complete emitted file set and each output SHA-256 with the manifest.
   Maintained README, examples, tests, and fixtures listed as excluded are not
   expected to be emitted by the generator.

The recorded NVVM run used Go 1.25.0 and Apple clang 21 on macOS arm64; it produced
all ten recorded files. Its headers came from libnvvm 13.3.33. The retained archive
and extracted header were checked locally against recorded provenance; the online
redistribution manifest was not freshly reverified.

System headers, compiler executable bytes, transitive Go module contents, and
upstream documentation identities remain incompletely pinned. Native execution
receipts are separate from this generation record. No supported runtime range or
native Windows/Linux ABI claim follows from matching generated bytes.

NVRTC uses the unmodified header from the verified cuda_nvrtc 13.2.51 archive.
Its header version is separate from the runtimes used for native tests. nvJitLink
uses its explicit pinned 13.0 header, which selects the intended versioned
symbols rather than those selected by the newer top-level header.

Run the local recorded-output regression gate from the `nvidia` module:

```sh
GOWORK=off go test -count=1 .
```

`TestUpstreamOutputs` checks every recorded output hash and rejects missing or
additional generated Go files in each recorded package. It recognizes `.gen.go`
filenames and standard `Code generated ... DO NOT EDIT.` comments, including
generated test files. Maintained source files are not generation outputs. The
mutation tests verify changed bytes, missing files and both forms of additional
generated files fail. This checks the currently recorded top-level Go output
sets only; unrecorded packages remain outside this partial manifest's evidence.
It does not run generation, verify vendor archives or establish runtime support.

Compute Sanitizer records 16 vendor headers and 15 generated files. Header provenance includes callback metadata headers whose declarations remain excluded from the host API surface; provenance does not imply binding coverage. The selected host-header ledger and native subscriber validation are separate evidence.

cuDNN records 35 reproduced files. Its seven original headers match the verified NVIDIA 9.20.0.48 CUDA 13 archive. The combined input is a locally derived, exact five-header concatenation; its ordered recipe is recorded separately from vendor archive members. This establishes matching byte provenance, not the historical download platform or runtime qualification.
