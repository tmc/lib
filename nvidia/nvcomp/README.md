# nvCOMP batched LZ4

Go bindings for the batched LZ4 entry points of NVIDIA's nvCOMP library,
generated by codegen's `gen-nvcomp`.

This is the low-level batched C API and nothing else: independent chunks, no
container format, no checksum, no metadata. The caller records how many chunks
there were and how large each one was; nothing in the compressed output does.
The nvCOMP manager classes are C++ and are not bound.

Size the workspace and the output with `CompressGetTempSizeAsync` (or
`CompressGetTempSizeSync`), `CompressGetMaxOutputChunkSize` and
`CompressGetRequiredAlignments`, launch with `CompressAsync`, synchronize the
stream, then check the per-chunk statuses with `CheckStatuses`. Decompression
is the same shape, with `GetDecompressSizeAsync` to recover the uncompressed
size of each chunk when the caller did not keep it.

`example_test.go` walks the whole sequence. It compiles and is not run.

## Status: implemented, physically unverified

Nothing in this package has been run against `libnvcomp`. It was written on a
machine with no CUDA libraries and no NVIDIA GPU, and the session that wrote it
could not reach one. No compression has been performed, no byte has moved to a
device, and nothing here has been measured.

What is checked, and runs anywhere:

- `abi_test.go` pins the bound symbol set against the symbol table of the
  pinned `libnvcomp.so.5.3.0.16`
  (`testdata/symbols-linux-x86_64-5.3.0.16.txt`), the Go type of every bound
  function pointer against the C prototype, the size, alignment and field
  offsets of the two by-value options structs, that a zero options value is the
  vendor default, the scalar widths the call sites assume, the result and
  option enum numbering, the header version constants, and that purego accepts
  every one of these signatures on the host running the test.
- `layout_test.go` (generated) asserts the same struct layouts from clang's
  record dump of the pinned headers, independently of the hand-written
  assertions in `abi_test.go`.
- `loader_test.go` (generated) checks that importing does not load, that an
  absent symbol yields `*SymbolError` rather than a panic, and that a
  conflicting `Load` fails loudly.

What is not checked, and what it would take:

- `pipeline_test.go` compresses a batch, decompresses it, compares the bytes,
  then corrupts one compressed chunk and requires that chunk's status to report
  the failure. It needs `libnvcomp.so.5` from the nvCOMP 5.3.0 redist, an
  NVIDIA driver with `libcuda.so.1`, and a visible GPU, and runs only with
  `NVCOMP_PHYSICAL_TEST=1`. It has never been run.
- `TestPropertiesMatchHeaders` in the same file needs `libnvcomp` but no GPU,
  and runs with `NVCOMP_LIBRARY_TEST=1`. It has never been run either.
- That purego lays out the by-value options struct the way the System V and
  AAPCS ABIs require. It is a 64-byte MEMORY-class argument in the middle of an
  eleven-argument call; `abi_test.go` shows purego accepts the signature, which
  is not the same as showing it passes the bytes correctly. Only a call into
  the real library can show that, and the cheapest such call is
  `CompressGetMaxOutputChunkSize`, whose answer changes with the options.
- That an address handed to a `Device`-prefixed parameter is really device
  memory. Go cannot express that. The distinct types mean a host address gets
  there only by a deliberate conversion, not by accident.

Both hardware-dependent tests fail rather than skip once their environment
variable is set, so a host that lacks a prerequisite reports that, instead of
reporting a pass.

## Device memory, and the pointer arrays

Every parameter with a `Device` prefix is an address in device memory, and each
kind has its own type so that a host address cannot reach one by an ordinary
assignment.

`DevicePointerArray` is the one worth reading twice. It is the device address
of an *array of device pointers*: the array itself must live in device memory,
not just the chunks it points at. Passing a host array here is not a Go type
error at the conversion site, and the failure it produces is an invalid device
access or silent corruption, not an error return. `SizeofDevicePointer`,
`SizeofDeviceSize` and `SizeofDeviceStatus` are the C element sizes for sizing
those allocations.

This package does not allocate, free or copy device memory and does not import
a CUDA package. Get addresses from whichever CUDA binding the program already
uses.

## Asynchronous completion

A nil error from `CompressAsync`, `DecompressAsync` or `GetDecompressSizeAsync`
means the launch was accepted. It does not mean the work ran and it does not
mean it succeeded.

Until the stream is synchronized, everything passed in must stay live and
unmodified: the temporary workspace, the input and output chunks, both pointer
arrays, the size arrays and the status array. After it completes, copy the
status array back and check every element. A chunk that failed says so there
and nowhere else, and an array that was never written reads as all zeros, which
is `Success` -- which is why the physical test corrupts a chunk and requires the
failure to show up.

## Header and library

Generated from `nvcomp/lz4.h`, `nvcomp/shared_types.h`, `nvcomp/version.h`,
`nvcomp.h` and `nvcomp_export.h` as shipped in the nvCOMP 5.3.0 (package
5.3.0.16, `cuda12`) redist archive, vendored and pinned with their sha256s
under `codegen/cmd/gen-nvcomp/headers/`.

Set `NVCOMP_LIB_PATH` before first use to select the library explicitly;
otherwise `libnvcomp.so.5` then `libnvcomp.so` are tried on Linux. There is no
macOS build of nvCOMP, so loading on darwin reports that no library names are
known for the platform.

The library exports the header's names undecorated. Twelve are bound: the ten
batched LZ4 calls plus `nvcompGetProperties` and `nvcompGetStatusString`. The
other 121 undecorated C symbols -- the same batched shape for eight other
codecs, CRC32, and the lower-level `bitcomp*` calls -- are not.

### A surface change since earlier releases

There is no `nvcompBatchedLZ4CompressGetTempSize` in 5.3.0. Earlier nvCOMP
releases had a single call by that name; this release splits it into
`CompressGetTempSizeAsync` and `CompressGetTempSizeSync`, and the Sync variant
takes the input pointer arrays and a stream because it inspects the actual
chunk sizes. Code written against the older name will not link against this
library, and `abi_test.go` asserts the old name is absent so that a future
regeneration cannot quietly reintroduce it.

## What this is for, and what it is not

The use case this was written for is staging, storing and transferring
checkpoints -- bytes at rest or in flight.

It is not an inference optimization. Nothing here has been measured, this
package makes no throughput or latency claim, and LZ4 on already-quantized
tensor data has no expected benefit worth asserting without a measurement.
Where the generated documentation recommends a chunk size or says a larger
alignment may help, that is NVIDIA's claim carried across as written, marked as
such, and not verified here.

## Regenerating

```
cd codegen && go run ./cmd/gen-nvcomp -output ../lib/nvidia/nvcomp
```

Generation requires clang: the parser needs a real AST for the by-value struct
layouts and the record dump that produces `layout_test.go`, and the generator
fails rather than fall back to the regex path. It also fails if a device
parameter in the header is not one it knows how to classify, or if either
default-options initializer in the header stops being all-zero -- that check is
what backs the claim that a zero options value is the vendor default.
