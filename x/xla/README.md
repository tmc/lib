# XLA

This module provides Go ownership wrappers for PJRT plugins, compiled programs
and device buffers. It uses `openxla` bindings and builds without cgo.

The [kvcache](kvcache) subpackage retains device key/value history for causal
attention, with reusable decode and prefill graphs.

Close buffers and executables before their engine. Execution waits for native
completion, including when its context is cancelled. Closing a resource must
be synchronized with calls that use it. A destruction error invalidates the Go
handle; it does not promise that the native runtime released the resource.

Uploads validate the byte length against the element type and dimensions.
Downloads validate destination size. Zero compile-option counts mean one;
negative counts are rejected. The compile-options encoder has no protobuf
library dependency.

Run `go test ./...` for host tests. To test the complete Go-to-PJRT path with a
CPU plugin installed separately:

```
XLA_PJRT_CPU_PLUGIN=/path/to/pjrt_c_api_cpu_plugin.so go test -run TestNative -v
CGO_ENABLED=0 XLA_PJRT_CPU_PLUGIN=/path/to/pjrt_c_api_cpu_plugin.so go test -run TestNative -v
```

The tests check compilation, host uploads, execution, output metadata,
downloads and resource cleanup using asymmetric matrix multiplication and
f16/bf16 attention generated by the StableHLO builder. Attention cases check
f32 accumulation, including inputs that would overflow an f16 dot product.
Mask tests cover causal prefill, cached decoding, per-batch padding, and fully
masked rows.
The tests are skipped when the environment variable is unset. They do not install a
plugin or validate TPU/GPU execution.

## Benchmarks and Go profiles

`BenchmarkNativePJRT` covers 64×64 and 512×512 F32 matrix multiplication.
It checks an asymmetric matrix multiplied by the identity before timing and
checks the final result afterward. `compile_close`, `upload_close`, and
`execute_close` include destruction of the resources they create. `download`
reuses its destination. Execute waits for native completion. Setup and validation
are excluded from benchmark time; CPU profiles can still sample that work.

Run from this module with a CPU PJRT plugin installed separately:

```sh
mkdir -p "$HOME/tmp/pjrt-profile"
export XLA_PJRT_CPU_PLUGIN=/path/to/pjrt_c_api_cpu_plugin.so
GOWORK=off CGO_ENABLED=0 go test -run '^$' \
  -bench '^BenchmarkNativePJRT$' -benchmem -count=8 \
  > "$HOME/tmp/pjrt-profile/bench.txt"
```

Profile one operation to avoid mixing compilation and execution:

```sh
GOWORK=off CGO_ENABLED=0 go test -run '^$' \
  -bench '^BenchmarkNativePJRT/512/execute_close$' -benchtime=3s \
  -cpuprofile="$HOME/tmp/pjrt-profile/cpu.pprof" \
  -memprofile="$HOME/tmp/pjrt-profile/heap.pprof" \
  -o "$HOME/tmp/pjrt-profile/xla.test"
go tool pprof -tags "$HOME/tmp/pjrt-profile/xla.test" "$HOME/tmp/pjrt-profile/cpu.pprof"
go tool pprof -http=127.0.0.1:0 "$HOME/tmp/pjrt-profile/xla.test" "$HOME/tmp/pjrt-profile/cpu.pprof"
go tool pprof -alloc_objects "$HOME/tmp/pjrt-profile/xla.test" "$HOME/tmp/pjrt-profile/heap.pprof"
```

Go CPU samples within the measured callbacks carry `pjrt.operation`,
`pjrt.shape`, and `pjrt.dtype` labels. Native PJRT worker samples may lack
these labels.
Go heap profiles do not carry these labels; select one benchmark when collecting
them. Profiles describe host Go work and waits, not device kernel durations.
Go allocation counts exclude PJRT's native allocator and device memory.
A missing plugin skips the benchmarks; a configured plugin that fails to load
fails the run. Retain the Go version, code revision, plugin checksum, benchmark
output, and matching test binary alongside profiles. Use repeated runs and
`benchstat` for comparisons; these operation benchmarks do not establish model
inference throughput.

## Native memory statistics

Call `engine.MemoryStats(device)` to query the PJRT allocator. `BytesInUse`
is reported on success; other fields are pointers and are nil when the plugin
omits them. A non-nil pointer to zero means the plugin reported zero.
The snapshot owns its values and remains valid after the engine closes.

Plugins can return an error when allocator statistics are unsupported. For
example, the tested CPU plugin reports `GetAllocatorStats is not supported`.
These counters complement Go heap profiles; they are not Go heap allocations,
per-operation allocation measurements, or proof of a leak. Allocator pools can
retain memory after buffers close.

To require native statistics from a plugin that supports them:

```sh
XLA_PJRT_MEMORY_STATS_PLUGIN=/path/to/plugin.so \
  GOWORK=off go test -run='^TestNativeMemoryStats$' -v
```

This opt-in test fails when the supplied plugin does not support the query.

Call `executable.CompiledMemoryStats()` for the compiler's estimates of argument,
output, alias, temporary, and other memory sizes. The wrapper releases its
temporary native metadata handle before returning and leaves the loaded
executable open. Query and cleanup errors are returned to the caller.

Compiled estimates are not live allocator counters. Unlike `MemoryStats`,
this PJRT API has no per-field availability flags: a zero can mean either zero
usage or an unpopulated field. Do not derive a total from `TotalBytes == 0` or
interpret it as evidence that a program needs no memory.

The native CPU test compiles a matrix product and checks its 80 argument bytes
and 24 output bytes on two successive queries:

```sh
XLA_PJRT_CPU_PLUGIN=/path/to/cpu/plugin.so \
  GOWORK=off go test -run='^TestNativeCompiledMemoryStats$' -v
```
